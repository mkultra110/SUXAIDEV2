## Architecture

```
┌────────────────────┐   JWT     ┌─────────────────────────┐   apiKey   ┌──────────────────┐
│ Electron + React   │ ────────► │ VPS (Express)           │ ─────────► │ Quatarly API     │
│  - Monaco          │           │  /auth  /ai  /update    │            │ api.quatarly.cloud│
│  - safeStorage     │ ◄──────── │  bcrypt + JWT + helmet  │ ◄───────── │                  │
└────────────────────┘  tokens   └─────────────────────────┘  SSE       └──────────────────┘
```

Key boundary: **the Quatarly API key lives only on the VPS**. Clients
authenticate with user-scoped JWTs. The `/ai/chat` endpoint is an SSE
streaming proxy that forwards to Quatarly and fans tokens back to the client.

## VPS deployment — DO NOT reinvent this

All SUXAI files on the VPS are isolated under `/opt/suxai/`:

```
/opt/suxai/
├── app/         # Node.js server code (rsync from repo's server/)
├── data/        # users.json, persistent state  (DATA_DIR, 0700)
├── logs/        # server.log
├── releases/    # installer binaries served at /releases/<file>
└── .env         # secrets (0600, owned by suxai)
```

- `sudo ./server/deploy/install.sh` — idempotent one-shot setup
- `./server/deploy/deploy.sh <user>@<host>` — subsequent updates
- systemd unit: `suxai-server` (hardened, runs as user `suxai`, not root)
- nginx site: `suxai` (SSE-friendly for `/ai/`, serves `/releases/` statically)
- Logs: `/opt/suxai/logs/server.log`

## Security posture — KEEP IT TIGHT

- The Quatarly API key `qua-17899503b9bf6973957a102d46c5a8dc` was disclosed
  during development and **must be rotated**. The new key goes **only** in
  `/opt/suxai/.env` on the VPS, never in git, never in the client bundle,
  never in the root user's shell env.
- `JWT_SECRET` is auto-generated by `install.sh` at first run (64-byte random).
- Client tokens are stored via Electron `safeStorage` (OS-level encryption),
  never `localStorage`.
- Renderer: `contextIsolation: true`, `nodeIntegration: false`, strict CSP.
- Updater: downloads over HTTPS, optional SHA-256 verification before
  launching installer.
- Password hashing: bcrypt rounds=12.
- Rate limiting on `/auth/*` (20/15min) and `/ai/chat` (30/min).

## Conventions

  `src/styles/theme.css`. No CSS-in-JS.
- Never commit: `.env`, `node_modules/`, `dist/`, `dist-electron/`, `release/`,
  `server/data/`.

  non-obvious. Match the existing style (see `git log`).

## Known sharp edges

- `vite-plugin-electron` resolves `./updater` without extension — don't add
  `.js` or `.ts` to that import in `electron/main.ts`.
- The SSE parser in `src/api/quatarly.ts` swallows malformed chunks silently
  — fine for production, but if debugging upstream issues, log them.
- On Debian/Linux, `safeStorage.isEncryptionAvailable()` is `false` unless
  the machine has `gnome-keyring` or `kwallet`. The code falls back to
  storing tokens plaintext in that case — flag if shipping on headless Linux.

### 4. Vérifier avant de considérer comme terminé
- Ne jamais marquer une tâche comme terminée sans prouver que cela fonctionne
- Repérer la différence entre le comportement principal et vos changements quand c'est pertinent
- Se demander : « Un ingénieur senior validerait-il cela ? »

### 5. Exiger de l'élégance (équilibrée)
- Pour les changements non triviaux : faire une pause et se demander « Y a-t-il une solution plus élégante ? »
- Si un correctif semble bancal : « Connaissant tout ce que je sais maintenant, quelle serait la solution élégante ? »

- Lorsqu'un bug est signalé : le corriger. Ne pas demander à l'utilisateur de le faire à votre place
